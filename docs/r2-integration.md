## Phase 8: approved copy-only migration of existing Supabase media

The owner-only Preview utility is available at `/business-owner.html?r2migration=1` on the `feat/r2-storage-integration` deployment. Sign in as a business owner, scan the businesses owned by that account, then use Copy and verify. Repeat while signed in as each owner account that owns source media. The scanner walks only the owner’s prefixes in `storenest-product-media` and `storenest-brand-media`; it reports supported image/video files and skips unsupported types or objects over 20 MiB.

The endpoint verifies the signed-in owner and business for every batch. It copies to `r2-supabase-migration/<source-bucket>/<owner>/<business>/...`, uses conditional writes, then reads each R2 object back to check its media type, byte count, and SHA-256 hash. A retry verifies an identical existing object and refuses to overwrite a different object. Migration is copy-only: Supabase originals, database URLs, storefront settings, listing state, and publication remain unchanged. The utility does not log session tokens, media bytes, or R2 credentials.

Keep the Supabase originals as rollback sources. This phase is complete only after each owner has scanned and copied all eligible objects, with no failed or skipped media requiring follow-up. The next phase must make verified R2 media available through the StoreNest customer and owner delivery paths, then update references safely and reconcile the database. Do not delete Supabase source objects as part of this Preview copy phase.


## Phase 9: Preview delivery of verified migrated public media

The feature Preview can display copied objects under the r2-supabase-migration/ prefix when opened with the query flag ?r2delivery=1. The display adapter matches only public object URLs from the Supabase storenest-product-media and storenest-brand-media buckets and only supported image/video file types. It redirects those requests through a Preview-only same-origin API endpoint, which signs a read-only Cloudflare R2 URL valid for 15 minutes. The R2 bucket stays private; the route accepts only the migration prefix for those two public source buckets and cannot read draft, catalogue-private, diagnostic, or other prefixes. The adapter setting persists for that browser tab session on this feature-branch Preview. Add ?r2delivery=0 to turn it off.

This is a display-only Preview check. It does not change database URLs, upload paths, listing state, approval decisions, or production. It does not delete or overwrite Supabase media. Supabase currently remains the source of truth and rollback copy. The API returns a one-object, time-limited R2 bearer URL to the browser; only objects from the two public source buckets can be requested. Do not place the R2 credentials or signed URLs in notes, chat, or logs.

After deployment, verify a customer storefront and an owner gallery with representative photos and video, then compare the R2-delivered media with the existing Supabase display. If any migrated object is missing, turn off r2delivery and recopy/verify that object. Production continues to use Supabase until a separate production cutover updates media references and all upload, authorization, publication, cache, and rollback paths. No Supabase source object should be removed until that cutover and an explicit retention decision.



## Phase 10: guarded production delivery and upload path

The feature branch now prepares the marketplace for a controlled production rollout without enabling it. Production remains on Supabase unless the marketplace Vercel project has R2 credentials and the explicit environment flags below. No production variables, domain aliases, database rows, or Supabase source objects are changed by this code.

- `R2_MEDIA_DELIVERY_ENABLED=true` permits the production read-signing endpoint to serve only verified objects under the existing `r2-supabase-migration/<source-bucket>/<owner>/<business>/...` prefix.
- `R2_MEDIA_DELIVERY_DEFAULT=true` makes production pages route eligible public media to R2 by default. Before this is enabled, `?r2delivery=1` is a production canary for the current browser session; `?r2delivery=0` opts that session back out.
- `R2_MEDIA_UPLOAD_ENABLED=true` enables normal owner product, responsive-image, logo, and storefront-cover uploads to R2. Production upload activation is rejected unless default R2 delivery is also enabled, so newly uploaded media cannot be saved without a matching display path.
- The upload API verifies business ownership, accepts only the existing public media buckets and owner/business-scoped safe keys, issues a five-minute conditional R2 PUT URL, and checks the stored content type, size, basic file signature, and SHA-256 hash after upload. The R2 access key and secret remain server-side.
- Direct browser uploads require the private bucket's CORS policy to allow PUT from only the exact StoreNest Preview and Production origins, with `Content-Type`, `Cache-Control`, and `If-None-Match`; the signed request also binds the expected `Content-Length`. The bucket must remain private; do not enable public bucket access.

The feature Preview still requires `?r2delivery=1` for reads. Preview uploads stay on Supabase unless both upload flags are explicitly enabled; do not enable them against the shared production Supabase database. After the code is merged and deployed to Production, first set only `R2_MEDIA_DELIVERY_ENABLED=true` and leave default delivery and uploads off. Test representative migrated images and video with `?r2delivery=1`, then remove the query flag and confirm normal Supabase rendering. Only after that canary succeeds should default delivery and R2 uploads be enabled together. Retain Supabase originals as rollback copies until the production cutover and follow-up retention decision are complete. New R2 objects are not automatically deleted on failed saves or listing removal; reconcile those separately to protect order history.


## Phase 9: isolated private approval-evidence credentials

The approval evidence routes now require dedicated R2 credentials instead of reusing the shared Marketplace media credential pair. The generic `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and `R2_BUCKET_NAME` remain reserved for existing catalogue/media behavior and are not changed by the evidence helper.

For each Vercel target, the evidence helper reads these exact variables:

- `STORENEST_APPROVAL_EVIDENCE_R2_ACCOUNT_ID`
- `STORENEST_APPROVAL_EVIDENCE_R2_ACCESS_KEY_ID`
- `STORENEST_APPROVAL_EVIDENCE_R2_SECRET_ACCESS_KEY`

The same names are used in HQ and Marketplace, but their values must differ by project and target. Marketplace should receive an R2 Object Read & Write token scoped to only the private evidence bucket, because it uploads, verifies, and may remove an unrecorded object. HQ should receive a separate Object Read only token scoped to that same bucket. Never share the Marketplace write token with HQ or with a Preview that points at another bucket. The account ID is not a secret; access keys are.

Production evidence continues to require the existing explicit source-code gates: `STORENEST_APPROVAL_EVIDENCE_PRODUCTION_UPLOADS_ENABLED=true`, `STORENEST_HQ_APPROVAL_WRITES_ENABLED=true`, production branch/database checks, and `STORENEST_APPROVAL_EVIDENCE_R2_BUCKET`. Preview remains separately guarded by `STORENEST_APPROVAL_PREVIEW_WRITES_ENABLED`, `STORENEST_APPROVAL_PREVIEW_SUPABASE_HOST`, and `STORENEST_APPROVAL_PREVIEW_R2_BUCKET`. Missing evidence-specific credentials now fail closed; there is no fallback to the shared media credentials.

No evidence bucket or evidence credentials were created or configured by this change. The proposed production bucket is `storenest-approval-evidence`, with public access, `r2.dev`, and public custom domains disabled. Do not use the public Marketplace media bucket for private documents. Creating a bucket, adding values to Vercel, or enabling the production flags remains a separate authorized step.

The endpoint continues to require an authenticated business-owner session, verify business ownership and listing/request context through the existing Supabase authorization paths, validate file type and the 2 MiB limit, verify uploaded bytes and SHA-256, detect duplicate submissions, and reconcile a failed database recording before cleanup. Private reads still require the owner session; HQ reads use the administrator-protected HQ endpoint. These are mocked CI checks, not a live R2 or production Supabase integration test.
