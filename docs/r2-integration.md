## Phase 2: real catalogue photo trial
Use /business-owner.html?r2trial=1 in the protected feature Preview. Open the existing item form, select a new JPEG/PNG/WebP/GIF up to 2 MiB, then click Test selected photo with Cloudflare R2. Use a non-sensitive test image. The test reuses the catalogue responsive-image generator and verifies each file separately by upload, byte equality, deletion and subsequent 404. Do not save the listing. No database writes, no production URL changes, and no original Supabase file changes. The server checks ownership, media signatures and payload limits; signature checks are not full image decoding or malware screening. This is not the production upload adapter. Larger uploads, private/public delivery, publication, and permanent storage/cleanup still need design and verification.

New images and generated variants persist privately in r2-catalog-draft/<owner>/<business>/; the catalogue row and R2 references are retained in browser localStorage only. The normal production save and Supabase file paths remain unchanged. Verify saved draft images performs an authenticated read and SHA-256 comparison, and Remove saved test draft deletes only the owner-scoped draft objects and verifies absence. Do not clear browser storage before cleanup. Failed/uncertain network writes may leave isolated draft orphans; inspect the prefix. This is not a public catalogue migration. A separate database, stable authenticated/publication-aware media delivery, complete upload limit support, lifecycle decisions and integration with approval/deletion flows are needed before production activation. No shared database writes are made by the isolated item save.

## Phase 4: persisted catalogue row (owner Preview only)
Use the protected feature Preview at /business-owner.html?r2catalog=1. The normal Add item / Save item action explicitly writes ONE new product to the connected live Supabase business_items table through existing owner RLS. It forces is_available=false regardless of the selector. No schema changes, existing listing updates or public release are performed. The user must intentionally create the product. Images are stored in r2-catalog-private/<owner>/<business>/ with durable r2://storenest-media/ references in image_url/media_urls and SHA-256 metadata. Owner Preview retrieves the cover through authenticated private API; ordinary legacy Supabase URLs continue unchanged. Private references are not browser-public URLs and the existing production owner UI cannot display them until the delivery adapter is released. Do not edit/publish these test rows from the production UI. No anonymous delivery, publication, registered media deletion or automatic cleanup on ambiguous DB errors. Existing isolated drafts are browser-origin-specific and are not imported automatically. Existing database lacks listing approval status columns; integrate approval branch and implement publication-aware media delivery and safe editing/deletion prior to production rollout. No production deployment or existing media migration is authorized here.

No public delivery or R2 hard deletion is enabled. Legacy listings use the existing path. Do not activate production until stable media delivery and approval enforcement are integrated. Browser and mocked tests do not replace live owner testing.

## Phase 8: approved copy-only migration of existing Supabase media

The owner-only Preview utility is available at `/business-owner.html?r2migration=1` on the `feat/r2-storage-integration` deployment. Sign in as a business owner, scan the businesses owned by that account, then use Copy and verify. Repeat while signed in as each owner account that owns source media. The scanner walks only the owner’s prefixes in `storenest-product-media` and `storenest-brand-media`; it reports supported image/video files and skips unsupported types or objects over 20 MiB.

The endpoint verifies the signed-in owner and business for every batch. It copies to `r2-supabase-migration/<source-bucket>/<owner>/<business>/...`, uses conditional writes, then reads each R2 object back to check its media type, byte count, and SHA-256 hash. A retry verifies an identical existing object and refuses to overwrite a different object. Migration is copy-only: Supabase originals, database URLs, storefront settings, listing state, and publication remain unchanged. The utility does not log session tokens, media bytes, or R2 credentials.

Keep the Supabase originals as rollback sources. This phase is complete only after each owner has scanned and copied all eligible objects, with no failed or skipped media requiring follow-up. The next phase must make verified R2 media available through the StoreNest customer and owner delivery paths, then update references safely and reconcile the database. Do not delete Supabase source objects as part of this Preview copy phase.
